# Skills, plugins & multi-client surface

> How the SDK presents itself to AI clients: skills, plugin manifests, slash commands, and the differences
> between Claude Code, Codex, and Desktop. The runtime "how to call tools" rules live in
> [`../agent-guide.md`](../agent-guide.md); this doc is the *what's installed and where* map.
>
> SSOT: `skills/*/SKILL.md`, `.claude-plugin/`, `.codex-plugin/`, `.mcp.json`, `mcp-server/src/prompts.ts` &
> `resources.ts`.

## Skills (`skills/`)

Each skill has a `SKILL.md` with YAML frontmatter (`name`, `description`) auto-discovered by the client:

| Skill | Role |
|---|---|
| `mimi-seed` | General entry point. Teaches deferred-tool loading (`ToolSearch select:`) and safety, then **branches** to the domain skills below |
| `mimi-seed-onboarding` | First-run onboarding: install check → `mimi_seed_status` scan → goal-based minimal credentials (`mimi-seed setup`) → first read-only action → hand-off. Answers "what can mimi-seed do?" from `mimi-seed://tools/catalog` |
| `playstore-publish` | Play Store listing / track release / image replace / review reply |
| `appstore-publish` | App Store Connect metadata, TestFlight builds, screenshots |
| `deploy` | End-to-end: CI build → readiness check → release notes → store apply |
| `video-create-publish` | Story/short-form video → typography and subject-safe crop review → render validation → optional YouTube publish |
| `game-intro-short` | Game Short from captured gameplay → verify the decision and result → localize and deliver |
| `pdf-design-quality` | Reader-facing PDF design, Korean typography, and render-based layout verification |
| `mimi-seed-update` | Upgrade an install to the latest server / skills / CLI, then verify the *running* version |
| `mimi-seed-install` | Install **from a clone**: `npm run setup` (both packages → build → `npm link` → `claude mcp add`), then hand off to `mimi-seed setup` for language + credentials |

The `mimi-seed` skill explicitly points deeper work at [`docs/agent-guide.md`](../agent-guide.md). Skill bodies
are written bilingually (Korean prose + English trigger lines); this ontology stays English per repo decision.

## Plugin manifests

| File | For | Notes |
|---|---|---|
| `.claude-plugin/plugin.json` | Claude Code plugin | `name: mimi-seed`, displayName "Mimi Seed"; bundles `skills/` + MCP from `.mcp.json` |
| `.claude-plugin/marketplace.json` | Claude Code marketplace listing | the plugin `source` is a release **tag** (`github` + `ref`), moved by `npm run release:marketplace` after npm publish — see below |
| `.codex-plugin/plugin.json` | Codex plugin | Korean descriptions, default prompts, brand color |
| `.codex-plugin/README.md` | Codex plugin docs | — |
| `.agents/plugins/marketplace.json` | Codex marketplace listing | Codex schema; do not reuse the Claude marketplace file |
| `plugins/mimi-seed/` | Codex marketplace distribution | Generated by `npm run plugin:sync`; CI rejects drift |
| `.mcp.json` | MCP registration | spawns the **local** server: `npx -y @yoonion/mimi-seed-mcp@<the plugin's version>` |

The root `.codex-plugin`, `.mcp.json`, `skills`, `docs`, `LICENSE`, `SECURITY.md`, and `.codexignore` are the Codex
distribution sources of truth. `scripts/sync-codex-plugin.mjs` materializes them under `plugins/mimi-seed` and also
writes the bundle's root `README.md` from `.codex-plugin/README.md` (links lifted one level); never edit that
generated copy directly. `npm run plugin:check` compares every file and is part of the root test command. Keep the
version fields in all plugin manifests in step when bumping.

`.mcp.json` pins the server to the **plugin's own version**, exactly. It used to say `@latest`, which runs
whatever npm serves at each spawn: one compromised publish path would execute on every user's machine, with
their `~/.mimi-seed/` credentials, before anyone noticed. Pinned, the server changes only when the plugin does.
`npm run version:set` moves the pin with the other version fields — for a **stable** version only; a prerelease
leaves it on the last stable release, because Codex reads `main` directly and would otherwise hand its users a beta.

**When users get a release is decided by the Claude marketplace entry, not by `main`.** Claude Code updates a
plugin only when its computed version changes (it is keyed on `plugin.json` `version`; a commit that leaves the
version alone never reaches users who already updated). The release order is "merge the version bump → tag →
CI → npm publish", so a marketplace that served `main` would hand out a plugin whose pinned server is not on npm
yet — every fresh install or update fails with `ETARGET` until the publish lands, or until a failed publish is
fixed. So `.claude-plugin/marketplace.json` points the plugin at a **release tag** —
`{ "source": "github", "repo": …, "ref": "v<version>" }` — and `npm run release:marketplace` moves that `ref` in a
follow-up PR, only after it has confirmed npm has the version and GitHub has the tag. Inside the tag, the plugin
version, the `.mcp.json` pin, and the npm package agree. `release-marketplace --check` (in `plugin:check`) holds
the shape: an exact stable pin equal to the root version (or below a prerelease root), no extra args / env /
registry in `.mcp.json`, and a stable `v…` tag of this repo that is never ahead of the root version.

Two consequences. A contributor testing the plugin from a checkout gets the **tagged** release from GitHub, not
the working tree, through the marketplace — use `claude mcp add` with the local build instead
([`../from-source.md`](../from-source.md)). And the **Codex** marketplace (`.agents/plugins/marketplace.json`) still
reads `plugins/mimi-seed/` on `main`; whether it can pin a git ref is not verified, so a Codex install made between
the release merge and the npm publish can fail to start until the publish lands.

The pin covers our package, not its dependencies: `npx` installs without a lockfile and resolves every `^`
range afresh. The published mcp-server therefore carries an `npm-shrinkwrap.json` — the one lockfile npm honors
inside a dependency — built at `prepack` by `scripts/shrinkwrap.mjs` from the committed `package-lock.json` with
the `dev` entries removed (left in, npm installs a shrinkwrapped package's devDependencies too: TypeScript,
Vitest, and ESLint land on every user's machine). It is never committed; `postpack` deletes it.

An already running stdio process still cannot update itself; reload the plugin or start a new client thread after
a release. That active-process distinction is the main reason the `mimi-seed-update` skill verifies the runtime
version.

## Slash commands & MCP resources

Exposed by the MCP server (`prompts.ts` / `resources.ts`, see [[architecture]]):

- **Server instructions** describe tool discovery, when to run connection diagnostics, and the preview-first write flow.
- **Prompts** include `/mimi-seed:getting-started` and `/mimi-seed:health`. The server exposes `/mimi-seed:deploy`
  and `/mimi-seed:review-inbox` when the active toolsets support the corresponding workflow.
- **Resources**: `mimi-seed://auth/status` (Google OAuth freshness, JSON), `mimi-seed://agent/guide` (the full
  [`docs/agent-guide.md`](../agent-guide.md), served from the committed copy `packages/mcp-server/assets/agent-guide.md`
  — refreshed by `npm run plugin:sync`, drift-guarded by `prompts-resources.test.ts`), and
  `mimi-seed://tools/catalog` (the active tools and their domain metadata from `tool-manifest.json`).

Clients surface these through their MCP prompt and resource support. Skills are packaged separately for Claude Code and Codex.

## Multi-client differences (matters for how tools appear)

| Client | Tool exposure | Context file it reads |
|---|---|---|
| **Claude Code** | tools are **deferred** — names visible, schemas load on demand via `ToolSearch select:` | `.claude/` (and the root `CLAUDE.md` that imports this ontology) |
| **Codex** | use the active client’s discovery when the schema is deferred | `AGENTS.md` |
| **Claude Desktop** | tools exposed directly | n/a (no project context) |

The deferred-tool behavior in Claude Code is the single biggest source of "this tool doesn't exist" mistakes —
it is the #1 entry in [[pitfalls]] and is documented for agents in [`../agent-guide.md`](../agent-guide.md) §0.

> Note: `mimi-seed init` scaffolds **the user's** project with `.claude/mimi-seed.md` + `AGENTS.md` so both
> clients pick up context there. That is separate from **this repo's** own `CLAUDE.md` / `AGENTS.md`, which
> point contributors at this ontology. Don't confuse the two ([[cli-deploy]]).
>
> Inside this repo the contributor context is mirrored per client and per package: root `CLAUDE.md` ↔
> `AGENTS.md` carry the same contract, and `packages/*/CLAUDE.md` simply `@`-imports the sibling
> `packages/*/AGENTS.md` so the package rules exist once. Change one, check the other.
